## 2-4. データフロー概要

アプリ全体のデータフローは以下の原則に従う。

**単方向データフロー:** View → ViewModel（ユーザーアクション）→
Model/Service（ビジネスロジック実行）→ Core Data（永続化）→
ViewModel（@Published更新）→ View（UI再描画）

**NSFetchedResultsController:**
フォルダ一覧・単語一覧などのリスト表示では、NSFetchedResultsControllerのデリゲートでCore
Dataの変更を自動検知し、ViewModelの@Publishedプロパティを更新する。

**B-03注記:** CloudKit初期同期時（大量データインポート）にNSFetchedResultsControllerのデリゲートが頻繁に発火し、UIが過度に再描画されるリスクがある。デリゲートの更新通知に0.5秒のdebounce（スロットリング）を適用することを推奨する。

**CloudKit同期:**
NSPersistentCloudKitContainerが自動的にiCloudとの同期を処理する。同期の競合はLast-Write-Wins方式で解決される。アプリ層ではCKAccountStatusの監視のみ行い、同期ステータス（有効/無効/エラー）をSettingsViewModelに公開する。

## 3-7. CloudKit統合設定

**NSPersistentCloudKitContainer:** Core
DataとCloudKitを統合する。コンテナ識別子は「iCloud.com.vocavault.app」とする。

**プライベートデータベース:**
全データはユーザー個人のiCloudプライベートデータベースに保存される。他ユーザーとのデータ共有は行わない。

**競合解決:**
Last-Write-Wins方式（NSMergeByPropertyObjectTrumpMergePolicy）を採用する。CloudKitのサーバータイムスタンプにより最新の変更が優先される。

**複数デバイス同時学習の検知・警告（H-03、H-03追加修正）:**
Last-Write-WinsではFSRSCardの状態依存データで学習データ消失のリスクがある（デバイスAとBで同一カードを学習した場合、一方のFSRS状態が上書きされる）。以下の対策を実装する。

① 【H-03追加修正】自デバイスでFSRSCard更新時にUserDefaults（vv_lastLocalReviewDate）に最終更新日時を記録する。FSRSCardエンティティへのデバイス識別子属性追加は行わない（CloudKitスキーマ変更を回避するため）。

② CloudKit同期受信時（NSPersistentCloudKitContainerの変更通知NSPersistentCloudKitContainer.eventChangedNotification）に、受信したFSRSCardのlastReviewDateがUserDefaultsのvv_lastLocalReviewDateより新しい場合、かつvv_lastLocalReviewDateが直近24時間以内（自デバイスでも最近学習した可能性がある期間）の場合に「別のデバイスで学習が行われました。最新の学習結果が反映されています」旨のバナー通知を表示する。

③ ReviewLogは両デバイスから追記されるため消失しないが、FSRSCard状態との不整合が発生しうる点を設計上の制約として記録する。Ph.2でカスタムマージポリシーの検討を行う。

**オフライン対応:**
NSPersistentCloudKitContainerはオフライン時にローカルCore
Dataストアに書き込み、ネットワーク復帰時に自動同期する。全学習機能はオフラインで完全動作する。

## 4-5. 主要数式

### 4-5-1. 忘却曲線（Retrievability算出）

**R(t, S) = (1 + F × t / S) \^ C**

F = 19/81 ≒ 0.2346,　C = -0.5

t = 前回復習からの経過日数,　S = 安定性

t = S のとき R ≒ 0.9（安定性の定義と一致）

### 4-5-2. 初期安定性（New → Learning 遷移時）

**S0(G) = w\[G\]**

G =
Grade（0〜3）のrawValue。初回評価のGradeに対応するw0〜w3が初期安定性となる。

### 4-5-3. 初期難易度

**D0(G) = w4 - exp(w5 × (G - 1)) + 1**

clamp(D0, 1.0, 10.0) で範囲を制限する。

### 4-5-4. 難易度更新

**D\'(D, G) = w6 × D0(3) + (1 - w6) × (D - w7 × (G - 3))**

平均回帰（mean reversion）により極端な値を防止。clamp(1.0, 10.0)。

### 4-5-5. 安定性更新（成功時: Hard/Good/Easy）

**S\'\_success = S × (1 + exp(w8) × (11 - D) × S\^(-w9) × (exp(w10 ×
(1 - R)) - 1) × hardPenalty × easyBonus)**

hardPenalty = G==Hard ? w16 : 1.0

easyBonus = G==Easy ? w17 : 1.0

### 4-5-6. 安定性更新（失敗時: Again）

**S\'\_fail = w12 × D\^(-w13) × ((S+1)\^w14 - 1) × exp(w15 × (1 - R))**

clamp(S\'\_fail, min: 0.01, max: S) で元の安定性を超えないようにする。

### 4-5-7. 次回復習日の算出

**scheduledDays = S\'**

安定性Sの定義が「再現性Rが100%から90%に低下するまでに要する日数」であるため、目標記憶保持率desiredRetention=0.9の場合、復習間隔は安定性S'そのものに等しい（C-01修正。FSRS調査資料 p.4の忘却曲線定義 R(t=S, S) = 0.9 に基づく）。

**将来的にdesiredRetentionをユーザー設定可能にする場合の汎用式:**

scheduledDays = S\' × ((desiredRetention\^(-2) - 1) / (19/81))

**dueDate = now + scheduledDays日**

scheduledDaysは最低1日（0日以下にならない）。max(1,
round(scheduledDays)) で整数化。

### 4-5-8. Easy成熟度ゲート（N-15追加）

新規カードの初期学習段階では、Easy評価が学習者の主観に依存しやすく、実際の記憶定着度を過大評価する可能性がある。十分な学習履歴が蓄積されるまで、Easyによる長期間隔化を抑制する。

**成熟度閾値の定義:**

カードが「Easy成熟」と判定される条件: reps >= 3 かつ (reps - lapses) >= 2

すなわち、少なくとも3回の学習機会を経て、そのうち2回以上で正答（Hard/Good/Easy）が確認された状態とする。

**Easy未成熟時の動作:**

  -------------------------------- ---------------------------------------------------------------
  **遷移**                         **Easy未成熟時の動作**

  New → Easy → Learning            初期安定性としてS0 = w2（Good相当）を適用する。
                                    w3は使用しない。D = D0(3) は通常通り適用。

  Learning → Easy → Review          S'\_success を算出するが、easyBonus = 1.0
                                    （ボーナスなし、Good相当の安定性増加）とする。

  Relearning → Easy → Review        同上。easyBonus = 1.0 とする。

  Review → Easy → Review            同上。easyBonus = 1.0 とする。
  -------------------------------- ---------------------------------------------------------------

**Easy成熟後の動作:**

reps >= 3 かつ (reps - lapses) >= 2 を満たした後は、通常のFSRS計算を適用する（S0 = w3、easyBonus = w17）。

**設計根拠:** FSRS調査資料（p.2）の「望ましい困難」の概念に基づく。初回Easy評価で約15日の間隔（w3=15.4722）が設定されると、Learning状態（🟡）のカードが長期間放置される不自然さが生じる。また、初期段階の主観的Easy判断は記憶定着と相関しにくいため、保守的な間隔設定が適切である。成熟度閾値を超えた後は、学習者の評価精度が安定していると判断し、FSRSの本来のEasyボーナスを適用する。

**通知の日次更新設計（C-02追加、R-07修正）:**

ローカル通知はスケジュール時点のコンテンツで固定されるため、通知内の復習対象数を正確に保つには再スケジュールが必要である。以下のタイミングでscheduleDaily()を再呼び出しし、通知を最新の復習対象数で再スケジュールする。

① アプリフォアグラウンド復帰時（ScenePhase.active検知）: CoreDataManager.fetchDueCount()で最新のdue数を再取得し、scheduleDaily()を呼び出す。【R-07修正】再スケジュール対象の判定は以下の通り:
  - 現在時刻が通知設定時刻より**前**の場合: **当日分**の通知を再スケジュールする（前日スケジュール時の古い件数を最新化）
  - 現在時刻が通知設定時刻**以降**の場合: **翌日分**の通知を再スケジュールする（当日分は既に発火済み）

② セッション完了時（ResultViewModelの初期化時）: 評価によりdueDateが変化するため、完了後に上記①と同一の判定ロジックで当日分または翌日分の通知を再スケジュールする。

③ 通知設定変更時（SettingsViewModelの時刻・ON/OFF変更時）: 既存のreschedule(at:)に加え、最新のdueCountで再スケジュールする。

FSRS調査資料（p.6）ではマイクロタスク形式の通知を推奨しているが、Ph.1では画面設計書S08制約で確定した「今日は○語の復習があります」（語数のみ）を正式フォーマットとする（I-04統一）。予想時間を含む形式（「今日はあと○分で○語の復習が完了します」）はPh.2以降の改善候補とする。

## 7-3. ディープリンク・状態復元

Phase
1ではディープリンク・状態復元は対象外とする。学習セッション中にアプリがバックグラウンドに移行した場合、セッション状態はメモリ上に保持され、フォアグラウンド復帰時に継続可能とする。アプリがシステムにkillされた場合、未保存の評価は失われる。

**セッション中データ保全（R-02対策）:** 最大100枚のセッションで途中killされた場合のデータ消失量を最小化するため、各カード評価完了時にCore Dataへ即座に保存する方式を推奨する（1件50ms以内のパフォーマンス要件内で許容可能）。E-01のメモリキュー方式と併用し、保存失敗時のみキューに退避する。
